# Проверка main и feature/parser-nucleotide-manifest

Дата проверки: 11 сентября 2026 года.

Проверены актуальные ссылки после успешного `git fetch origin --prune`: `origin/main` — `521b293`, `origin/feature/parser-nucleotide-manifest` — `257bf56`. Feature является продолжением main: 9 дополнительных коммитов, 16 изменённых файлов, 893 добавленные и 91 удалённая строка. Локальная ветка совпадает с origin.

Это ревью репозитория, а не аудит работающего сервера. Серверные overrides, переменные Compose, фактические контейнеры, занятые порты и конфигурация действующего Nginx не предоставлены. Поэтому причины, зависящие от серверного состояния, ниже сформулированы условно.

### 1. Высокий приоритет: dev может пересоздать production

В обеих ветках `docker-compose.yml:1` задаёт `name: alignmabzoo`, а строка 4 — один и тот же сервис. Разные имена каталогов checkout сами по себе не обеспечивают изоляцию. Без переопределения имени проекта обычный `docker compose up -d` в dev управляет тем же Compose-проектом и может пересоздать production-сервис с dev-образом и другим mount jobs. `docker compose down` из dev также относится к тому же проекту.

Сборка использует общий тег `alignmabzoo-alignmabzoo`. Одна только сборка не заменяет уже работающий контейнер, но следующий запуск/пересоздание может взять другой образ. Приоритет имени проекта: `-p`, затем `COMPOSE_PROJECT_NAME`, затем `name:`. Это подтверждается [документацией Compose](https://docs.docker.com/compose/how-tos/project-name/); формат тега — [документацией build](https://docs.docker.com/reference/cli/docker/compose/build/).

### 2. Высокий приоритет: одного `-p` недостаточно для общей сети

При разных проектах контейнеры останутся в общей `internal-net` с одинаковым service alias `alignmabzoo`. Nginx обращается именно к нему (`nginx/alignmabzoo.conf:10`). Выбор контейнера для общего alias не гарантирован; запросы к production могут попасть в dev. Добавление отдельного dev alias без устранения общего имени сервиса не устраняет неоднозначность production-адреса. См. [правила сетевых aliases](https://docs.docker.com/reference/compose-file/services/#aliases).

Нужно разнести имена сервисов либо сети и upstream. При сохранении общей сети предлагается сервис `dev-alignmabzoo` и отдельный Nginx virtual host с `proxy_pass http://dev-alignmabzoo:8000`.

### 3. Порты и расположение Nginx

В Git main не занимает host:5000 и не публикует host:8000. Следовательно, по этим двум compose нельзя заключить, что main непосредственно блокирует dev порт 5000. Причину ошибки bind нужно искать среди действующих контейнеров, host-процессов и серверных overrides.

`127.0.0.1:5000` предназначен для доступа с самого сервера. Обращение к `<внешний-IP>:5000` обычно не попадёт в этот bind. Для Nginx в другом контейнере `127.0.0.1` означает сам Nginx-контейнер, а не хост приложения. При схеме из плана Nginx обращается через `internal-net`, и публикация 5000 вообще не нужна. Для Nginx, установленного непосредственно на хосте, loopback-публикация может быть нужна; тогда upstream должен использовать выбранный host-порт. См. [документацию публикации портов](https://docs.docker.com/engine/network/port-publishing/).

Одинаковые `listen 80` у разных virtual host одного Nginx допустимы. Проблема текущего шаблона — одинаковые `server_name` и upstream. Повторное подключение копии конфигурации не создаёт dev-маршрут.

### 4. Jobs разделены, но совместное использование несовместимо

Коммит `333ee64` исправил общий jobs mount. Текущая feature использует `alignmabzoo-dev/jobs`; README продолжает описывать только production-путь. Само имя каталога `alignmabzoo-dev` допустимо, даже если сервис называется `dev-alignmabzoo`: важно явно зафиксировать выбранный путь.

Общий jobs-root опасен не только параллельной записью. Feature добавляет `parent_job_id` и `sequence_ids` в `JobRecord` (`job_registry.py:93`), а сериализация сохраняет эти поля даже для обычных job (`job_registry.py:390`). Main использует `extra="forbid"` и не знает новых полей. После записи реестра feature main не сможет прочитать его, при этом `REGISTRY_VERSION` остался равен 1. Это также ограничение отката с feature на main с сохранением нового реестра. Нужны изолированные каталоги и явная политика миграции/отката.

### 5. Общая для обеих веток ошибка многопроцессности

`Dockerfile:98` запускает Gunicorn с `--workers 2`. `_job_semaphore` в `job_pipeline.py:34` — обычный `asyncio.Semaphore`, а блокировка реестра `job_registry.py:117` — `threading.RLock`. Они не общие между процессами.

Возможные последствия: до четырёх вычислительных job в одном контейнере вместо двух; потерянные изменения при одновременном read-modify-write реестра; запуск recovery в новом worker может перевести job живого соседнего worker в `failed`. Атомарная замена JSON защищает целостность отдельной записи, но не всю транзакцию чтения и изменения.

Для текущей архитектуры практическое минимальное исправление — один ASGI worker при двух фоновых job и проверка отсутствия блокирующей работы в event loop. Полноценное сохранение двух workers требует межпроцессной очереди, блокировки реестра и координации recovery. Изолированные prod/dev не делят лимит: два запуска на каждую версию означают четыре на сервере; общий серверный лимит потребовал бы отдельного решения.

### Новые расхождения и незавершённые решения

- `parsed_chains.txt` и `chains_named.fasta` теперь одинаковы по заголовкам: `>seq_<hash>` (`job_pipeline.py:348–361`). Первый потерял требуемый `<проект>/<группа>/<имя>`, второй перестал непосредственно содержать нормализованное имя. Manifest хранит имя отдельно, но изменение пользовательского формата FASTA не закреплено в плане. Технические ID можно оставить внутреннему FASTA либо явно согласовать новый контракт.
- Сохраняется ориентированная DNA выбранной feature, однако manifest не сохраняет `codon_start`, координаты/ID feature, таблицу трансляции и проверку соответствия qualifier `translation`. При рамке 2/3 или stop raw DNA не является готовой последовательностью кодонов выбранного белка. Это подготовка к V(D)J, а не завершение его координатного контракта.
- `Dockerfile:17` использует `MMSEQS_GIT_REF=master`. Запись фактического SHA в `/usr/local/share/mmseqs2-revision` полезна для аудита, но не закрепляет следующую сборку: она может получить другой код или reuse старый слой cache. План требует проверяемую закреплённую версию. Следует закрепить commit и проверить именно этот образ/CPU на сервере.
- README не описывает dev project/service/порт/путь результатов, новые артефакты и realign API. Исследовательские документы местами описывают старое состояние: отсутствие DNA в ParseResult, формирование ID из имени, нерешённость разбиения MSA. Это нужно синхронизировать с кодом и принятыми решениями.

### Унаследованные расхождения с AGENTS

- `parser.py:17`: минимальная длина 80 aa вместо 20.
- `alignment.py:26`: Other не входит ни в один пакет основного MSA, хотя AGENTS требует сохранять такие строки в выравнивании.
- Парсер рассматривает features не только типа CDS; длинная транслируемая feature может обойти CDS.
- `naming.py:157–166`: fallback по животному идёт раньше fallback по двум из трёх символов проекта.
- `alignment.py:78`: сортировка по нормализованному имени, а не исходному имени файла.
- `queued` после перезапуска не восстанавливаются в очередь: startup обрабатывает только running.

Наличие этих отличий в main подтверждено; не следует приписывать их девяти коммитам feature. Для минимальной длины, naming и парсинга следует проверить историю согласований перед изменением поведения.

## Предлагаемая конфигурация изоляции

Для архитектуры с Nginx в `internal-net`:

| Настройка | Production | Development |
|---|---|---|
| Compose project | `alignmabzoo` | `dev-alignmabzoo` |
| Service | `alignmabzoo` | `dev-alignmabzoo` |
| Внутренний порт | 8000 | 8000 |
| Host ports | не нужны | не нужны; отдельный loopback-порт только для диагностики |
| DNS upstream | `alignmabzoo:8000` | `dev-alignmabzoo:8000` |
| server_name | `alignmabzoo.<домен>` | `dev-alignmabzoo.<домен>` |
| Host jobs | `.../alignmabzoo/jobs` | `.../alignmabzoo-dev/jobs` |

Сменить именно ключ сервиса, а не только container_name или добавить alias. У каждого окружения должны быть собственные команды управления, checkout и образ. Общий read-only data-root допустим. TLS и DNS для dev-поддомена на сервере требуют отдельного подключения. Это предложение для последующего исправления, оно не применялось к серверу.

Для подтверждения реального конфликта достаточно сначала выполнить на сервере чтение состояния:

```sh
docker compose ls
docker ps -a --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'
sudo ss -ltnp '( sport = :5000 )'
docker network inspect internal-net
```

В каждом checkout отдельно посмотреть `docker compose config` и `git rev-parse HEAD`. Для найденных prod/dev-контейнеров посмотреть `docker inspect`: Compose labels, mounts, network aliases и port bindings. Проверить реально загруженный Nginx config через `nginx -T` в том окружении, где Nginx работает. До идентификации project не использовать `down` для диагностики.
