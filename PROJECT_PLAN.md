## 1. Общие сведения

### 1.1. Назначение приложения ✅
Веб-приложение для обработки SnapGene `.dna` и GenBank `.gb` файлов с последовательностями
моноклональных антител: парсинг белковых последовательностей, нумерация CDR (anarci),
мультивыверивание (Clustal Omega) и интерактивный просмотр выравниваний.

### 1.2. Роль ИИ-агентов ✅
- ИИ-агенты (оркестратор + субагенты) используются **только в процессе разработки** приложения:
  оркестратор создаёт субагентов для изолированных задач (написание модулей, ревью, отладка).
- Само приложение **не содержит LLM-компонентов** — это детерминированный пайплайн.

### 1.3. Пользователи ✅
- Запуск на сервере по SSH, доступ через браузер.
- **Несколько пользователей одновременно** → нужен веб-сервер с поддержкой
  параллельных сессий и изоляцией job'ов.

### 1.4. Язык документации и интерфейса ✅
- Русский.

## 2. Архитектура

### 2.1. Стек ✅
- **Backend:** Python, **FastAPI** (выбран вместо Flask: асинхронность, авто-документация OpenAPI,
  удобная интеграция с фоновыми задачами).
- **Frontend:** React + TypeScript + MUI (существующий `AlignmentViewer.tsx` уже написан
  на React/MUI и ожидает API `getAlignment(jobId)` → фронтенд строим вокруг него).
- **Сборка фронтенда:** Vite; собранный статический фронтенд раздаётся тем же FastAPI.

> **GUI (PyQt/Tkinter) — почему не выбран.** Вариант GUI рассмотрен и отклонён:
> - **Несколько пользователей по SSH** — GUI требует X11-туннелирования для каждого
>   пользователя (медленно, хрупко, неудобно); веб-интерфейс работает в любом браузере
>   без дополнительной настройки.
> - **AlignmentViewer.tsx** уже написан на React/MUI — с GUI пришлось бы переписывать
>   его на QTableWidget/QWidget с потерей готовой функциональности (CDR-подсветка,
>   консенсус, Zappo, перестановка строк, тултипы).
> - PyQt/Tkinter не дают «бесплатно» параллельные сессии, историю job'ов,
>   скачивание файлов, live-логи — всё это тривиально в вебе.
> - PyQt5/6 — тяжёлая зависимость (~100+ МБ), Tkinter — ограниченный виджет-набор
>   (нет удобных чекбоксов-дерева, таблиц с прокруткой, темизации).
> Вывод: **FastAPI + React** — минимальные потери и максимальное переиспользование
> существующего кода.

### 2.4. Модель job'а ✅
- Job = один запуск пайплайна по набору выбранных (животное → проекты → группы).
- Каждый job получает уникальный ID (UUID) и **свою папку** (см. 3.2).
- Job'ы изолированы: параллельные пользователи не мешают друг другу.
- Состояние job'а: `queued → running → done | failed | partial`
  (`partial` = завершён с ошибками по отдельным файлам, отчёт собран).

## 4. Пайплайн

### 4.1. Шаг 1: Извлечение ID и типа цепи ✅
Вход: имя файла (без расширения). Выход: `ID = <ТипЦепи>_<Клон>`.

**Алгоритм извлечения клона:**
1. Определяем название проекта (из имени папки проекта, без кода животного).
   Название проекта = префикс до первого `-<цифра>` (например, `PTH-3` → `PTH`,
   `AFP-L3` → `AFP`). ❓ Q3: подтвердить правило «префикс до `-<цифра>»`.
2. Ищем в имени файла вхождение названия проекта.
3. Клон = все буквы/цифры **после** названия проекта, до первого спецсимвола
   или знака табуляции.
4. Если точное вхождение не найдено — проверяем **неполное вхождение**:
   совпадение хотя бы **2 из 3** символов названия проекта.
   Пример: проект `Gt PTH-3`, файл `VHeavy_cDNA_Gt_PT92485` →
   `PT` совпадает с `PTH` (2 из 3) → клон `PT92485`, ID `VHeavy_PT92485`.
5. Если не удалось найти — ID = имя файла (без расширения).

**Нормализация типа цепи** (замены, регистр — ❓ Q4: case-sensitive или нет?):
| В имени файла | → Тип цепи |
|---|---|
| `HC`, `VH`, `HeavyC` (и `VHeavy`) | `VHeavy` |
| `VK`, `VK1`, `V1K`, `K1C`, `KC`, `KC1`, `kappa1`, `Kappa`, `Kappa1`, `KappaC` (и `VKappa`) | `VKappa` |
| `LC`, `LC1`, `LC2` (и `VLambda`) | `VLambda` |

После нормализации ожидаются только `VHeavy`, `VKappa`, `VLambda`.
❓ Q5: что делать, если тип цепи не определяется (нет ни одного ключевика)?
Предлагаю: отдельная группа `Other` в выравнивании + запись в лог.

### 4.2. Шаг 2: Парсинг белковых последовательностей ✅
- `.dna`: autosnapgene.
  1. Берём CDS features (если нет — любые features с нуклеотидными сегментами).
  2. Если qualifier `translation` непустой — используем его.
  3. Иначе транслируем из нуклеотидной последовательности (Biopython):
     учёт `codon_start`, обратная цепь (reverse complement),
     обрезка по стоп-кодону.
- `.gb`: Biopython (SeqIO genbank), аналогичная логика.
- Из всех кандидатов выбираем **самую длинную** белковую последовательность.
- Минимальная длина белка: 20 aa (как в существующем `main.py`). ❓ Q6: оставить?
- Лог: для каждого файла — исходное имя → новый ID (чтобы пользователь видел
  переименования).

### 4.3. Шаг 3: Anarci ✅
- Для каждой белковой последовательности запускаем anarci **3 раза**:
  `--scheme imgt`, `--scheme kabat`, `--scheme chothia`.
- Результат каждой схемы сохраняем в отдельный CSV:
  `<имя_последовательности>_<схема>.csv` в `<проект>/jobs/<job_id>/anarci/`.
- Данные валидированные: в каждом файле ровно 1 цепь строго в 1 рамке
  считывания → ожидаем успешную нумерацию.
- ❓ Q7: формат CSV — стандартный вывод anarci (таблица с номерами позиций),
  или нужен свой формат (например, `position,amino_acid,imgt_number`)?
  Существующий `AlignmentViewer.tsx` ожидает на фронтенде `numbering.imgt/kabat/chothia`
  как массивы номеров по позициям выравнивания — значит backend должен сам
  собрать из CSV anarci эти массивы. Подтвердить, что CSV anarci — «как есть»
  из anarci, а преобразование в формат viewer'а делает backend.
- ❓ Q8: последовательности, которые anarci **не нумерует** (exit code ≠ 0 /
  нет результата) — включать в выравнивание без нумерации + запись в лог?
  (Предлагаю: да, включать, помечать в отчёте.)

### 4.4. Шаг 4: Clustal Omega ✅
- Вход: все белковые последовательности job'а.
- **Одно общее выравнивание** (один `.aln`), в котором цепи **сгруппированы блоками**:
  1. все `VHeavy` вместе,
  2. все `VKappa` вместе,
  3. все `VLambda` вместе.
- Внутри блока порядок — **по имени файла** (алфавитный).
- Перед запуском clustalo входной FASTA сортируется в этом порядке,
  чтобы блоки сохранились в `.aln`.
- Команда: `clustalo -i input.fasta -o alignment.aln --threads N`
  (❓ Q9: фиксировать `--threads`? по умолчанию все ядра).
- `ANARCI` с HMM-базой загружается при `docker compose build`, а `hmmer` и `clustalo`
  устанавливаются в образ; после сборки их доступность проверяется внутри контейнера.
  Приложение также проверяет их наличие при старте job'а и даёт понятную ошибку.

### 4.4.1. Формат выравнивания для viewer'а ✅
- `AlignmentViewer.tsx` ожидает **несколько групп** (`AlignmentResponse.groups`),
  где каждая группа — `AlignmentGroup { name, sequences[] }`.
- Backend формирует **3 группы** (одна на тип цепи) из **одного общего `.aln`**:
  - `VHeavy` — все VHeavy-строки выравнивания (в порядке блока),
  - `VKappa` — все VKappa-строки,
  - `VLambda` — все VLambda-строки.
- Для каждой последовательности:
  - `seq` — строка из `.aln` (с гэпами);
  - `numbering.imgt/kabat/chothia` — массивы номеров по **позициям выравнивания**
    (сдвигаются с учётом гэпов: номер берётся из CSV anarci по порядковому
    номеру аминокислоты в исходной последовательности, гэпы → `null`);
  - `cdr.imgt/kabat/chothia` — `{ cdr1: number[], cdr2: number[], cdr3: number[] }`
    — позиции CDR **в координатах выравнивания** (индексы строк `.aln`).
- Таким образом: **один `.aln` на диске**, а в viewer'е — три панели
  (VHeavy / VKappa / VLambda), каждая со своим консенсусом и CDR-подсветкой.

### 4.5. Шаг 5: Подача результата ✅

  ```json
        ]
      }, ...

  }
  ```
- ❓ Q10: CDR-позиции (`cdr.cdr1/cdr2/cdr3`) — брать из вывода anarci

- Фронтенд: `AlignmentViewer` показывает группы VHeavy/VKappa/VLambda

### 4.6. Обработка ошибок ✅
- Ошибка на одном файле (не парсится, anarci упал, пустая последовательность)
  **не прерывает** job: пайплайн продолжается с остальными.
- В конце — **отчёт об ошибках**: список файлов с причинами
  (в `report.json` и в лог, показывается на фронтенде).
- Статус job'а: `done` (без ошибок) или `partial` (с ошибками).

### 4.7. Логирование ✅
- **Единый лог-файл** на job на проект: `<проект>/jobs/<job_id>/log.txt`
  (job из нескольких проектов → по одному лог-файлу в job-папке каждого проекта;
  все логи одного job'а имеют общий `job_id` и доступны со страницы job'а).
- В лог:
  - сколько файлов найдено/выгрушено;
  - сообщения об ошибках;
  - логи парсинга с новыми именами (старое имя → новый ID);
  - количество файлов, вышедших из anarci (успешно/неуспешно);
  - логи выравниваний (команда, время, размер).
- Лог доступен пользователю на фронтенде (страница job'а, автообновление).

## 5. Интерфейс (Job Wizard) ✅

### 5.1. Шаг 1: выбор животных
- Чекбоксы: 10 животных (код + название). Можно выбрать одно или несколько.

### 5.2. Шаг 2: выбор проектов
- Для каждого выбранного животного — список его проектов (папки первого уровня).
- Если выбрано **одно** животное — названия проектов **без** префикса животного.
- Если **несколько** — названия **с** префиксом животного (`Gt PTH-3`, `Ov AFP-L3`).
- Галочки: пользователь снимает/ставит проекты.

### 5.3. Шаг 3: выбор групп (отдельно для каждого проекта, по очереди)
- Для каждого выбранного проекта по очереди окно:
  «Использовать все группы для этого проекта?»
  - **Подтвердить** → все папки групп проекта.
  - **Выбрать конкретные** → чекбоксы папок групп (только первый уровень).
- Дополнительная галочка в правом углу окна: **«применить ко всем проектам»**
  (выбранный набор групп / «все группы» применяется к остальным проектам).

### 5.4. Запуск
- Кнопка **«Запустить пайплайн»** → создаётся job, пользователь видит
  страницу job'а: статус, прогресс по шагам, лог (live), по завершении —
  выравнивания (AlignmentViewer) + отчёт об ошибках.
- Процесс идёт **без участия пользователя**; результат = выравнивания + логи.

### 5.5. Просмотр результатов
- `AlignmentViewer` (адаптированный) — основной вид результата.
- Страница job'а: список проектов, количество последовательностей по цепям,
  ссылки на `.aln`/CSV (скачивание), лог, отчёт об ошибках.
